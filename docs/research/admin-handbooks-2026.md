# The admin plan against the handbooks (for milestone 15)

Checked on 27 November 2026, against the plan in [admin-2026.md](admin-2026.md), [admin-ux-2026.md](admin-ux-2026.md), `docs/reviews/M15.md` (the foundation and the six screens) and D-553. Each claim cites a page with the date it was read, or a file and line in the installed source:

- WordPress 7.1.5 and WooCommerce 11.3.1: `~/.wp-env/wp-env-csb-g-45ce68cc/wordpress-7/` and `.../woocommerce/` (lane checkout `csb-g`).
- WordPress 7.0.2, the nearest 7.0 on disk: `~/.wp-env/6bd2d1426c1bd31c28e1d2bfadb8e1ce/WordPress/`. 7.0.8 isn't on disk; its private APIs should match 7.0.2's, since a minor release doesn't move `wp-components`, but the spike's run on 7.0.8 is the proof.
- `@wordpress/dataviews` 12.0.1: `/Users/zach/web-projects/csb-g/node_modules/@wordpress/dataviews/`.
- `@wordpress/dataviews` 22.0.0, `@wordpress/ui` 0.26.0, `@wordpress/components` 44.0.0 and 45.0.0, `@wordpress/views` 1.7.1: unpacked from npm (`npm pack`) into a scratch folder to read them, not installed in the repository.

The short version: the plan's shape holds (the server form, hidden inputs, one PHP description, `validity`, tables with modals). But the pinned release stops working on WordPress 7.2, which ships on 8 December 2026, inside this milestone. The plan also misses six interactions with WordPress's and WooCommerce's own scripts.

## Findings by source

### 1. Gutenberg: `@wordpress/dataviews`, DataForm and the packages they lean on

1. **WordPress 7.2 removes most of the private APIs that 12.0.1's plain build calls.** 12.0.1 takes these from `wp-components` through `unlock( privateApis )`: `ValidatedInputControl`, `ValidatedTextareaControl`, `ValidatedSelectControl`, `ValidatedCheckboxControl`, `ValidatedNumberControl`, `ValidatedRadioControl`, `ValidatedToggleControl`, `ValidatedToggleGroupControl`, `ValidatedComboboxControl`, `ValidatedFormTokenField`, `DateCalendar`, `DateRangeCalendar`, `Menu`, `Badge` and `kebabCase` (12.0.1 `build-module/components/dataform-controls/*.mjs`, `components/dataviews-item-actions/index.mjs:15`).
   - **7.0.2 and 7.1.5 have all of them** (`wp-includes/js/dist/components.js:56277` in 7.0.2, `:56023` in 7.1.5), which is why the spike passed.
   - **Components 44.0.0, the release WordPress 7.2 ships,** keeps only `ValidatedInputControl`, `ValidatedTextareaControl`, `ValidatedContentEditableControl`, `Badge`, a deprecated `Menu` (removal planned for 7.3) and five others (`src/private-apis.ts` in 44.0.0 and 45.0.0, and in Gutenberg `c5bdc7f`, the commit `wordpress-develop`'s `7.2` branch builds from, `package.json:10`, read 27 Nov 2026).
   - **When they went:** components 39.0.0 (12 Aug 2026) dropped `DateCalendar`, `DateRangeCalendar`, `kebabCase` and the select, checkbox, number and radio controls. 40.0.0 (26 Aug 2026) dropped the combobox, token field, toggle and toggle group controls, which "now live internally in `@wordpress/dataviews`, its only consumer" ([components CHANGELOG](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/CHANGELOG.md), read 27 Nov 2026).
   - **The effect on 7.2:** each of those names is `undefined`. A select, radio, toggle, toggle group, checkbox, integer, number, combobox, array or date control renders an undefined component, and React throws. A row action that opens a modal calls `kebabCase()` (`dataviews-item-actions/index.mjs:58`) and throws. Only text and textarea fields survive. That covers nearly every screen in the plan.
   - **When:** WordPress 7.2 is due on 8 December 2026 ([RC3 post](https://wordpress.org/news/2026/11/wordpress-7-2-release-candidate-3), 24 Nov 2026, read 27 Nov 2026). The plan moves the newest leg to 7.2 if it ships during M15, and a site that auto-updates gets it on release day.
2. **22.0.0's plain build uses no private API at all.** It never imports `@wordpress/private-apis`; its 30 named imports from `@wordpress/components` are all public, and all 30 exist in 7.0.2's and 7.1.5's `components.js`. Its imports from `wp-compose`, `wp-element`, `wp-data`, `wp-date` and `wp-keycodes` all exist in both too (checked name by name, 27 Nov 2026). It bundles `@wordpress/ui` 0.26.0, `@wordpress/kebab-case` and `@wordpress/react-inert-value`, which wp-scripts never maps to WordPress (`dependency-extraction-webpack-plugin/lib/util.js:2`, 7.2.0). Two more checks:
   - `@wordpress/ui` 0.26.0 opts in to private APIs under its own name, and reads `ThemeProvider` from `wp-theme`, as a public export or through its private APIs (`build-module/utils/theme-provider.mjs`). `@wordpress/ui` is in 7.0.2's and 7.1.5's allowlist (`private-apis.js:72` in 7.1.5), and both releases' `theme.js` expose `ThemeProvider` privately.
   - 22.0.0 asks for React `^18 || ^19`; 7.0 and 7.1 ship React 18.3.1 (`script-loader.php:109`).

   So 22.0.0 should load on 7.0, 7.1 and 7.2 alike. It is also the release 7.2 bundles ([7.2 field guide](https://make.wordpress.org/core/2026/11/20/wordpress-7-2-field-guide), 20 Nov 2026, read 27 Nov 2026). This is a static check only; the spike has to run it on all three. Its weight is unmeasured. `@wordpress/ui` is the heavy part (342 kB minified in [admin-2026.md](admin-2026.md)), so expect far more than 12.0.1's 63 kB. The 26 November figure for 22.1.0's DataForm, 160 kB compressed, is the likely order.
3. **Core asks plugins that bundle DataViews to move to 22.0.0 before 7.2.** Bundled copies of `@wordpress/ui` and `@wordpress/dataviews` built before the fix share CSS module class names, so two copies on one page style each other ([Update bundled @wordpress/* packages](https://make.wordpress.org/core/2026/11/16/update-bundled-wordpress-packages-and-wordpress-build-to-fix-css-module-class-name-collisions/), 16 Nov 2026, read 27 Nov 2026: `@wordpress/ui` 0.26.0 and `@wordpress/dataviews` 22.0.0 are the first fixed releases). From 7.2 core's own copies no longer collide with an old one, but two old copies, ours and another plugin's, still can. The same post's comments advise against bundling `@wordpress/components` in WordPress, since its class names clash with the global `wp-components` stylesheet. That supports D-553's plain build over the `/wp` build.
4. **The handbook still says plugins built with wp-scripts should import `@wordpress/dataviews/wp`** ([package page](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-dataviews/), read 27 Nov 2026; the [DataForm settings post](https://developer.wordpress.org/news/2026/01/how-to-use-dataform-to-create-plugin-settings-pages), 20 Jan 2026, read 27 Nov 2026, says the same). The reason was the private APIs: the plain import crashed in plugins ([#65126](https://github.com/WordPress/gutenberg/issues/65126), Nov 2024). In 12.0.1 that advice protects against exactly the break in finding 1. In 22.x the reason is gone, since there are no private APIs left to call, and the `/wp` build would bundle a components copy against WordPress's stylesheet (finding 3).
5. **DataForm's controls use the browser's own constraint validation.** `ControlWithError` calls `setCustomValidity()` on the real input for every `invalid` rule, and on an `invalid` event it suppresses the browser's bubble and focuses the first invalid control in `target.form` (`components.js:55395` to `:55440`, 7.1.5). The card and panel layouts call `reportValidity()` on their inputs once touched (`src/hooks/use-report-validity.ts`, 12.0.1). Inside our host forms, `#post` (`wp-admin/edit-form-advanced.php:473`) and `#mainform` (WooCommerce `includes/admin/views/html-admin-settings.php:151`), neither of which has `novalidate`, this means:
   - a client rule that fails blocks the whole submit, so the client decides, against principle 2 ("client rules are hints, the server decides");
   - a failing control in a hidden product data panel, or a closed card or details group, can't be focused, so Update does nothing visible;
   - a server error passed in through `validity` keeps its input invalid until `validity` changes, so if the kit holds the server's answer unchanged after an edit, the form can't be sent again.

   [#73015](https://github.com/wordpress/gutenberg/issues/73015) (Nov 2025) documents that this design intercepts native validation. Components 38.0.0 added that only trusted `invalid` events move focus, so a synthetic `invalid` shows a message without moving the user (changelog, #80685). 7.0 ships 32 and 7.1 ships 37, so neither has it.
6. **A card's `summary` names fields, not text.** `CardSummaryField` is a field id, a list of ids, or `{ id, visibility }` objects (`build-types/types/dataform.d.ts:35`, 12.0.1; the package page lists the same). The summary shows those fields' values in the header. `Card.php` in `csb-g` prints a translated sentence ("Assembly off, no fee"), which DataForm would read as a field id. Three more card details:
   - `isOpened` is a prop the card copies into its own state when it changes (`card/index.tsx:116` to `:123`), so a server error can open a card at mount, as `Form::failed()` intends;
   - the validation badge shows only after the card was touched (`card/index.tsx:153`), so a closed card with a server error shows no badge unless it is opened;
   - the card's title is a `<span>` in 12.0.1 (`card/index.tsx:243`) and a `<div>` in 22.0.0 (`Card.Title` from `@wordpress/ui`, `card/title.mjs:5`), not a heading. A `headingLevel` option is in trunk's Unreleased section (#87390), in no published release.
7. **Each rule works only on some field types** ([DataViews, DataForm, et al. in WordPress 7.0](https://make.wordpress.org/core/2026/03/04/dataviews-dataform-et-al-in-wordpress-7-0), 4 Mar 2026, read 27 Nov 2026). `pattern`, `minLength` and `maxLength` work on text, email, telephone and url fields; `min` and `max` on integer and number fields only. The plan types measures as text so they take "8 1/4", so the Wheelbase's `min` 10 and `max` 20 would do nothing; only a `custom` rule checks a range on a text field.
8. **`prefix` and `suffix` are React components,** not strings (`EditConfigText`, `build-types/types/field-api.d.ts:76` to `:86`, 12.0.1). The JSON can carry a string, and the kit turns it into a component.
9. **The `validity` object has a fixed shape** (package page, read 27 Nov 2026):
   - its keys are field ids, and a field with no problem is left out;
   - each rule takes `type` (`invalid`, `validating` or `valid`) and `message`, and only `required` may leave the message out;
   - `children` holds a combined field's parts, which Deck range needs.

   Since 12.0.0, DataForm marks the smaller group of fields as required or optional on its own (12.0.1 `CHANGELOG.md`, #74430), so our labels must not add "(required)" themselves.
10. **`@wordpress/views` keeps views under the shared `core/views` scope, not a scope of ours.** Its key is `dataviews-${kind}-${name}-${slug}` (`src/preference-keys.ts`, `src/use-view.ts:64` to `:132`, 1.7.1). The preferences store sends it to `POST /wp/v2/users/me`, saved in the `{prefix}persisted_preferences` user meta, and keeps a copy in `localStorage` under `WP_PREFERENCES_RESTORE_DATA` (`wp-includes/js/dist/preferences-persistence.js:95` to `:133`; `script-loader.php:382` to `:396`; `user.php:5227`). The versions that pair:
    - `@wordpress/views` 1.7.1 (npm tag `wp-7.0`) asks for `@wordpress/dataviews` ^12.0.1;
    - 3.1.0 asks for ^22.0.0;
    - 3.2.0 asks for ^22.1.0.

    npm's tag `wp-7.0` for dataviews is 12.0.1, which confirms D-553's pin matches 7.0's own (`npm view`, 27 Nov 2026). DataViews' `onReset` prop shows Reset view only when persistence is wired (package page).
11. **Stylesheets.** Within WordPress the package page asks for `wp-components` as a dependency of the plugin's stylesheet. `wp-components` depends on `wp-theme`, which serves `design-tokens.css` (`script-loader.php:1767`, `:1836`). 12.0.0 stopped embedding those tokens in DataViews' own stylesheet (12.0.1 `CHANGELOG.md`). The package ships `build-style/style-rtl.css` beside `style.css`. wp-admin's stylesheet already pulls in `wp-base-styles`, the admin colour schemes (`script-loader.php:1641`), so DataViews' primary colour follows the user's scheme.
12. **The bundled package's own strings are in WordPress's `default` domain** (`__( "Search" )` with no domain): 133 strings in 12.0.1, 144 in 22.0.0, plus 31 in `@wordpress/ui` 0.26.0. `wp_set_script_translations()` for our handle loads only our domain. In 7.1.5 with fr_CA:
    - only 10 of 12.0.1's strings are in `wp-components`' JSON, so most stay English on our screens;
    - core's copies sit in the JSON for `wp-media-utils` (116 of 133 for 12.0.1, 124 of 144 for 22.0.0), `wp-edit-site`, `wp-editor` and the `content-types` script module;
    - four of 12.0.1's strings ("Collapse", "Expand", "Enable infinite scroll", "Validating…") are in no core JSON.

    Each JSON file is named by the MD5 of the script's path, which is how they were matched (`wp-content/languages/fr_CA-*.json`).
13. **Accessibility notes in the docs.** The package page says the DataViews parts handle keyboard, focus and roles, and that a free composition owns its outer structure. Since 11.2.0 a table row is selected only by its checkbox or Ctrl/Cmd-click (12.0.1 `CHANGELOG.md`, #73873), which helps a table whose rows carry a Fix link. 11.2.0 also fixed column moving in RTL (#74644, #74681).

### 2. WordPress Plugin Handbook and Common APIs

1. **Script translations.** `wp_set_script_translations( $handle, $domain, $path )` is at `functions.wp-scripts.php:342` and `load_script_textdomain()` at `l10n.php:1143`. The JSON is found by the MD5 of the script's path relative to the plugin, which the `load_script_textdomain_relative_path` filter can change (`l10n.php:1316`). `composer i18n:pot` scans `build/` and leaves out `assets/src`, so each string's reference points at the built file, and `make-json` names the JSON after it. That is right for our own strings. The bundled package's `default` strings never enter our POT (finding 1.12).
2. **Admin notices.** `wp_admin_notice()` and `wp_get_admin_notice()` exist since 6.4 (`functions.php:9196` and `:9307`), and the plugin already uses them (`src/Plugin.php:232`). Core's `common.js` moves every `div.notice`, `div.updated` and `div.error` that isn't `.inline` to just after `.wp-header-end` once the page is ready (`wp-admin/js/common.js:1090`). So an error summary printed inside a form or card jumps to the top unless it carries `inline`. A React `Notice` from `wp-components` has the class `components-notice`, so it stays put.
3. **Leaving warnings.** Core's product screen has its own `beforeunload` for the title and content only (`wp-admin/js/post.js:479`), and turns it off when `#post` is submitted (`post.js:366` to `:393`). WooCommerce's settings page has its own, below (section 3). The product page has none for meta, so the kit's warning is needed there, and like core's it must turn off when the form is submitted.
4. **Loading only on our own screens.** The plan's per-screen check holds (`BuildTabHooks::styles()` checks `$screen->id === 'product'`, `src/Admin/BuildTabHooks.php:57`). But the kit product type is chosen in the browser: WooCommerce shows the panel by its `show_if_cbuild_kit` class (`src/Admin/BuildTab.php:233`) and fires `woocommerce-product-type-change` when the type changes (`assets/js/admin/meta-boxes-product.js:265`). A new product, or a simple product turned into a kit, has no kit in the database when the page loads.
5. **Plugin Check 2.2.0** (the version in wp-env, `plugin-check/plugin.php`):
   - its new `React_Usage_Check` reports a build that inlines React, as an error, ahead of WordPress's move to React 19. It warns on `ReactDOM.render`, `hydrate`, `unmountComponentAtNode`, `findDOMNode` and `createFactory` (`includes/Checker/Checks/General/React_Usage_Check.php:18` to `:40`, `:512` to `:538`). It reads every JavaScript file in the zip (`:159`), so the admin bundle's third-party code is read too.
   - `Enqueued_Scripts_Size_Check` (300,000 bytes) visits front-end addresses only (`Performance/Enqueued_Scripts_Size_Check.php:148` to `:170`), so it never weighs the admin's entries. `npm run budget` remains the only gate on them.
6. **Plugin directory guideline 4** asks that compressed code ship with its source or a link to it ([detailed guidelines](https://developer.wordpress.org/plugins/wordpress-org/detailed-plugin-guidelines/#4-code-must-be-mostly-human-readable), linked from Plugin Check's `Minified_Files_Check`). The zip leaves out `assets/src` and `package.json` (`.distignore`). The readme credits three.js and ships its licence (`readme.txt:47`), but names no bundled admin code.

### 3. WooCommerce developer docs and source

1. **The Settings UI is still experimental and opt-in** ([Settings UI](https://developer.woocommerce.com/docs/extensions/settings-and-config/settings-ui), read 27 Nov 2026; `includes/react-admin/feature-config.php:9`, `settings-ui => false`). Even with the flag on, a tab keeps the classic renderer unless it returns an adapter from `get_settings_ui_page()`, so our tab is never converted behind our back. Its `form_post` serializer, read in `assets/client/admin/settings-ui/index.js`:
   - sends a checkbox as `yes` or `no`, never absent;
   - sends a list as `name[]` entries;
   - refuses any name deeper than `name[key]`.

   Our names nest deeper (`cbuild_mapping[0][attribute]`), so its adapter couldn't carry them. A field whose component is missing "fails closed" with a Use classic settings link. WooCommerce's own bundle carries its own DataViews and components copy (2.1 MB, with the private-API opt-in inside), and loads only on pages that opt in.
2. **WooCommerce's `settings.js` already watches the settings form** (`assets/js/admin/settings.js:106` to `:175`):
   - Save starts disabled (`html-admin-settings.php:181`);
   - on any `change` or `input` of an input, select or textarea it enables Save and sets `window.onbeforeunload` to its own "changes will be lost" prompt;
   - elements inside `.wc-settings-prevent-change-event` are ignored;
   - a `MutationObserver` on `#mainform` binds the listener again, and enables Save, whenever nodes holding inputs are added or removed. Mounting DataForm inside the form enables Save at once.

   The listeners use jQuery's `.on()`, which receives native events, so a native bubbling `change` from a hidden input enables Save. Without that event, the browser would send the new value but WooCommerce wouldn't know the form changed.
3. **Variations save by AJAX, and only those marked as changed.**
   - `input_changed` is bound with delegation to `change input` on `#variable_product_options .woocommerce_variations :input` (`meta-boxes-product-variation.js:656` to `:660`). It adds `variation-needs-update` to the variation, and `save_on_submit` sends only variations with that class (`:937` to `:948`). A hidden input set by script without a bubbling `change` is never saved.
   - The variations are loaded and paged by AJAX, which empties the wrapper (`:795` to `:803`), and the script announces it with jQuery's `woocommerce_variations_loaded` on `#woocommerce-product-data`, a jQuery event that `addEventListener` never receives.
   - Paging with unsaved changes asks `window.confirm` (`check_for_changes`, `:700` to `:720`).
4. **The block product editor is gone** (deprecated in 10.9, removed in 11.0; [Product editor beta retiring](https://developer.woocommerce.com/2026/06/02/product-editor-beta-retiring), 2 Jun 2026, read 27 Nov 2026). The classic product data panels are the only home for the Build tab and Part specs, so building there is right.
5. **WooCommerce's direction for extension settings** is one design system: cards, forms and data views from the WordPress Design System, not custom components ([Unifying extension settings](https://developer.woocommerce.com/2026/07/08/unifying-extension-settings-in-woocommerce), 8 Jul 2026, read 26 and 27 Nov 2026). The UX guidelines already in [admin-ux-2026.md](admin-ux-2026.md) still stand; nothing in them changed after 26 November.
6. **WooCommerce's settings save** checks `manage_woocommerce` and the `woocommerce-settings` nonce (`class-wc-admin-settings.php:87`, `:91`), and our tab checks both again (`src/Admin/SettingsPage.php:367` to `:371`). That holds with hidden inputs, since they post through the same form.

### 4. Accessibility and the admin's design

1. **Card titles aren't headings in any published release** (finding 1.6). A screen reader user who moves by heading can't jump between the cards of Settings or the Build tab, which matters under WCAG 2.4.6 and 1.3.1. The WordPress accessibility team's handbook, now kept on GitHub ([Make WordPress Accessible](https://make.wordpress.org/accessibility/), read 27 Nov 2026), asks for a logical heading outline on admin screens.
2. **Focus on errors.** Validated controls move focus to the first invalid control on a trusted `invalid` event (finding 1.5). With our server answer arriving on a fresh page load, nothing moves focus; the plan's one notice at the top that links to each field is what a keyboard user starts from. Its links must land on the real input, inside an opened card and the right product data tab.
3. **The admin design system.** WordPress's design tokens arrive as the `wp-theme` handle, and the colour schemes as `wp-base-styles` (finding 1.11). The 2026 tokens work is the [Design System Theming merge proposal](https://make.wordpress.org/core/2026/07/07/merge-proposal-design-system-theming) (7 Jul 2026, read 27 Nov 2026). 7.2 replaces Dashicons in the admin menu with inline SVG and moves the editor's menus to `@wordpress/ui`'s `Menu` (7.2 field guide). Nothing in 7.2 asks a plugin's admin page to change its layout. There is no core "admin page" handle yet: `@wordpress/admin-ui` is on wp-scripts' bundled list (`util.js:3`), not a WordPress script.
4. **WCAG 2.2** points from [admin-ux-2026.md](admin-ux-2026.md) (dragging, focus not obscured, target size, redundant entry) are unchanged.

## What this changes in our plan

Ranked by impact. Each item is a confirm, a change or an addition, with the concrete change.

1. **Change: re-pin `@wordpress/dataviews` to 22.0.0, the plain build, before any screen is built** (findings 1.1 to 1.4). 12.0.1 breaks on WordPress 7.2, due 8 December, on every control but text and textarea, and on every row action with a modal.
   - Run the spike again on 7.0.8, 7.1.5 and 7.2 RC3, the last with a version pin of its own for the trial. Check every control the screens use (select, radio, toggle, toggle group, combobox, integer, checkbox, the modal action, bulk actions), not only the five the first spike checked.
   - Measure the entry, compressed at Brotli 11, and set D-554's lines from it. If it passes about 250 kB, it goes to Zach.
   - Pair it with `@wordpress/views` 3.1.0, exact (it asks for ^22.0.0).
   - Rewrite D-553 with the reason and the 7.2 evidence.
   - Add a gate, in `composer gates` or a Vitest case, that greps the pinned package's `build-module` for `unlock(` and fails if a release brings private APIs back.
   - Fallback if 22.0.0 fails on 7.0: the `/wp` build of 22.0.0, with the stylesheet mismatch on 7.0 and 7.1 checked by the visual project.
2. **Change: decide how the host form treats DataForm's native validation** (finding 1.5). Test first:
   - a failing hint in the Build tab while General is open must not leave Update doing nothing;
   - a server error must clear once its field is edited;
   - Save must still send after a refused save is corrected.

   I recommend that the kit set `form.noValidate = true` on `#post` and `#mainform` while it is mounted, and on submit open the card and tab of the first field its rules flag, while still letting the POST go so the server decides. Record it as a decision; the cost is that another plugin's native `required` on the product screen stops blocking too. The kit also drops a field's server `validity` the moment that field's value changes. `Field::rules()` gains a unit test that a rule on the wrong type is refused (next item).
3. **Change: hold each rule to the types DataForm applies it to** (finding 1.7). `Field::rules()` refuses `min` and `max` on a text field and `pattern` or `maxLength` on an integer. Measures typed as text (Wheelbase, the deck range's sizes) get a `custom` rule that parses the measure the way `Domain\Measure` does, as a hint, with the server's check unchanged.
4. **Change: a card's summary becomes a read-only field computed from the form's values** (finding 1.6). `Card::closed()` takes the id of a summary field, not a sentence. The field's `getValue` builds the text from the current data with the translatable patterns printed from PHP ("Assembly on, %s fee"), so the header doesn't go stale as the user types. A card with a server error is opened at mount (`isOpened`), since the badge alone shows only after a touch.
5. **Add: the hidden-input contract fires a bubbling native `change` on each input it writes** (findings 3.2 and 3.3). On Settings that enables WooCommerce's Save and its leaving prompt. On a variation it adds `variation-needs-update`, without which the variation isn't saved. A Playwright case per screen edits one field through DataForm, saves, and reads the value back.
6. **Add: the Settings tab uses WooCommerce's leaving prompt, not the kit's** (finding 3.2). The kit's warning is off on WooCommerce settings pages. DataViews' search, filters and row checkboxes in the mapping table sit inside `.wc-settings-prevent-change-event`, so searching the table doesn't count as a change. Save being enabled as soon as the form mounts is WooCommerce's own behaviour, recorded rather than fought. On the product screen the kit keeps its own warning, turned off on `#post`'s submit as core does (`post.js:393`).
7. **Add: variation forms follow WooCommerce's AJAX lifecycle** (finding 3.3).
   - Mount on jQuery's `woocommerce_variations_loaded`, listened to with jQuery, and on a panel's opening.
   - Unmount every root with `root.unmount()` before WooCommerce empties the wrapper (paging, save, add), or the roots leak.
   - Keep the hidden inputs inside `.woocommerce_variation` with WooCommerce's `name[loop]` names.
   - A test pages through 20 variations twice and checks that nothing is mounted twice and no edit is lost.
8. **Change: saved views live in `core/views`, and uninstall and PRIVACY.md say so** (finding 1.10). The plan says "under the plugin's own scope"; `@wordpress/views` has none. Use `kind: 'cbuild'`, so our keys are `dataviews-cbuild-{screen}-{view}`. Uninstall removes only those keys from `core/views` in each user's `{prefix}persisted_preferences`, and the test keeps another plugin's key in the same scope. PRIVACY.md lists the user meta and the browser's `WP_PREFERENCES_RESTORE_DATA` copy, which uninstall can't reach.
9. **Add: give the bundled package's strings core's translations** (finding 1.12). Before each admin handle, print `wp.i18n.setLocaleData( …, 'default' )` with the messages of `load_script_textdomain( 'wp-media-utils' )`. It is a core API on a core handle registered on every admin page, so it adds no file of ours.
