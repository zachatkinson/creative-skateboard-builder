# Security checklist

Walked before each tag by someone other than the author of the milestone. OWASP's top ten mapped to a WordPress plugin, plus the spec's own rules. Each line is marked with the tag it was walked for and a word on how.

## Rules the code is held to (spec: Security, performance and compatibility)

1. Nothing from the browser is trusted. A build link, a preset or a form carries IDs only; each is checked on every use, and prices are always the server's.
2. The state route is public and read-only: a GET with an explicit `permission_callback`, a schema for its arguments, a rate limit per address and `Cache-Control: no-store`. It shows only what the shop shows. Its `Server-Timing` header (1.1.0, D-304) goes only to a signed-in user who can manage WooCommerce.
3. Every admin action checks a capability and a nonce. Input is sanitised where it arrives and output is escaped where it is printed.
4. SQL only in `src/Repository/` and `src/Install/`, always prepared. Products and orders only through WooCommerce's CRUD. CI: PHPCS `WordPress.DB`, PHPStan and `tools/gates.sh` (gates 1 and 1b).
5. No user data is unserialised and no PHP object is stored. `unserialize`, `eval`, `extract` and the shell functions are banned (gate 2).
6. No outbound request but the update manifest and the release it names (gate 5). The updater reads only the agency's manifest, over HTTPS with no redirect followed, takes a package only from this plugin's own releases in the agency's releases repository, and checks the zip's SHA-256 before WordPress installs it.
7. Saved builds are read and changed only by the customer who owns them, checked on every request.
8. Generated files are made only for builds that pass validation, from a capped queue, and named by a hash, never by anything a visitor sends.
9. Logs hold part, kit and order IDs, never names, emails or addresses.
10. Supply chain: both lock files committed, `composer audit` passing, `npm audit` passing on what the zip ships (D-044), a secrets scan on every push, every GitHub Action pinned to a commit SHA, a CycloneDX SBOM with each release, the zip's SLSA build provenance signed on a runner with no secret and nothing of the toolchain (`gh attestation verify <zip> --repo zachatkinson/creative-skateboard-builder`, from 1.1.0; D-299), the workflows linted by actionlint and zizmor on every push, and the release's token never on a runner that installs or runs the toolchain (D-043, gate 9).
11. Uninstall removes everything the plugin made and keeps the shop's order records.

## The repository (from 18 November 2026, D-237)

The repository is public. These hold what reaches `main` and what a release publishes; each is a GitHub setting, read back with `gh api` when a release is walked.

- **Who can write:** Zach alone. Anyone else can fork and open a pull request, and a pull request from outside runs no workflow until Zach approves it (`fork-pr-contributor-approval`: all external contributors).
- **`main`** (ruleset "main"), with no one able to bypass it, Zach and Claude Code included:
  - no force-push and no deletion;
  - every change through a pull request, merged as a merge commit;
  - the CI jobs green before the merge, by their exact names: the seven of 18 November, and from D-258 the five `Browser (…)` jobs beside the newest leg;
  - review threads resolved.
- **Release tags** (ruleset "release tags", `refs/tags/v*`): a tag can be created, never moved or deleted, so a version always names the code `release.yml` published.
- **Secrets:** GitHub's secret scanning and push protection on; gitleaks in CI on every change; the full history scanned clean before the repository went public (gitleaks 8.30.1, every branch).
- **Actions:**
  - only GitHub's own and three named actions (`gitleaks/gitleaks-action`, `ramsey/composer-install`, `shivammathur/setup-php`) may run, each pinned to a full commit SHA;
  - workflows read by default, and can't approve pull requests.
- **Reporting:** private vulnerability reporting on, so a hole is reported without a public issue.
