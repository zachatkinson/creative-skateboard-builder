# Accessibility

Two layers. axe-core runs in CI on every screen and state the plugin draws (Playwright, `tests/e2e/support/axe.ts`), failing on any violation of the WCAG 2.0, 2.1 and 2.2 A and AA rules. Once per release, a person who did not write the code runs the scripted pass below with VoiceOver on Safari (macOS and iOS) and NVDA on Firefox, and records the result here.

## Rules (spec: Quality bar, Accessibility)

- Every control works from the keyboard, in an order that follows the page, with a focus ring that is always visible and never covered by the phone bar.
- Fit changes, the picture's description and the total are announced once per pick through a polite status region that is in the page from the start.
- The picture has one written description that changes with the build.
- The page reflows at 320 CSS pixels with no two-way scrolling, holds up with text spacing raised, and keeps targets at 24 by 24 CSS pixels or more.
- Forced colours and reduced motion are respected.
- Every admin screen is built from WordPress's own admin markup and passes axe.

## What 0.1.0 draws

One thing: the notice on the Plugins screen when PHP, WordPress or WooCommerce is below the floor, shown to people who can manage plugins. It is printed by `wp_admin_notice()`, so it has WordPress's own markup and role, and its text is one translatable sentence.

The smoke test runs axe on the plugin's row of the Plugins screen in eight browser projects: Chromium, WebKit and Firefox at desktop and phone widths, fr_CA, and right to left (he_IL). It cannot run in the ninth, where scripts are off, since axe is a script. Two links in that row are WordPress core's and are left out, with the reason at the call: "View details", and "Visit plugin site", whose label and text differ in core's fr_CA and he_IL language packs.

On the shop, a product, the cart and the checkout the plugin draws nothing, and the test asserts that in all nine projects. axe is not run there (D-035).

## What 0.3.0 draws

**WooCommerce > Settings > Builder.** The form is WooCommerce's, with its heading, tabs and Save button. The plugin's two fields are plain controls with no script:

- each line of the mapping is a `fieldset` whose legend is "Line N", and its three controls each have a visible label tied to them by `for`;
- the three places of the source order are one `fieldset` with a legend, each list with a visible label and the field's description as its `aria-describedby`;
- a refused save puts each problem in a notice beside its field, sets `aria-invalid` on the controls it is about and points their `aria-describedby` at it, and WooCommerce's own error notice at the top says nothing was saved;
- nothing depends on colour, and the layout is the same single column at every width, so it holds at 320 px and at 400 % zoom.

`settings.spec.ts` saves a mapping and an order from the keyboard alone, saves a wrong line and reads its problem, and runs axe on the plugin's fields, at desktop and phone widths.

**The Part specs panel,** on a product and inside each variation. WooCommerce draws the tab, the variation's row and the save buttons; the plugin draws the fields:

- every field has a visible label tied to it by `for`, with its unit in the label, never in a placeholder: "Deck width (in)";
- the fields are in eight groups, one per kind of part, each a native `details` element whose `summary` opens it from the keyboard. A group opens by itself when it holds a value. The summary is a target 34 pixels high (WCAG 2.2, 2.5.8); the browser's own was 18, which axe caught;
- a value in use that is not the field's own (the parent product's, a mapped attribute's, a maker's chart's) is a sentence beneath the field, tied to it by `aria-describedby`, so a screen reader hears it with the field and nobody takes it for something to edit;
- a group that is closed has its fields disabled, so they send nothing (0.3.1, D-104). They are inside a closed `details`, which no keyboard or screen reader reaches, and are enabled the moment the group opens, before focus can arrive;
- in a variation the fields are one `fieldset` with the legend "Part specs". On the product the tab names the panel, and a `fieldset` there breaks WooCommerce's label layout;
- a value that is wrong is named in WooCommerce's own notice after the save, with the field's name and what was typed. It is not tied to the field: the notice is WooCommerce's, at the top of the screen on a product and above the variations after their save.

`part-specs.spec.ts` fills a product in from the keyboard, reads the notice for a wrong value, names a size in a maker's chart on a variation and reads where each figure comes from, with axe on the panel in each state, at desktop and phone widths. It skips where scripts are off: WooCommerce shows the product data box's tabs and loads its variations with a script.

**WooCommerce > Builder, Spec tables.** Three pages of the plugin's own, each a plain form post that works with scripts off:

- the list is a table with a header row, each chart's name its row's header and a link to the chart;
- a chart is a `fieldset` per size, its legend "Row N: size 149", with nine fields each under a visible label. The fields sit side by side where there is room and wrap where there is not, so nothing scrolls sideways at 320 px. The first draft of the settings tab showed why this is not a table: at phone width a table's headers part from their cells;
- a chart that is refused comes back as it was typed. Each row's problems are a notice inside the row's group, the fields they are about carry `aria-invalid` and point at the notice with `aria-describedby`, and a notice at the top says nothing was saved;
- deleting is a page of its own that asks first, with the chart's name in its heading, a button that deletes and a link that keeps: no script, so no dialog.

`spec-tables.spec.ts` adds a chart from the keyboard, fills in a row, has a wrong figure refused and reads its problem, saves, and deletes, at desktop and phone widths with axe in each state, and with scripts off without it.

**WooCommerce > Builder, Import and export.** A tab of the same page, each form a plain post that works with scripts off:

- the page's three tabs are links in a `nav` named "Builder", and the one being shown carries `aria-current="page"`;
- the file field and the "Match parts by" list each have a visible label tied to them by `for`; the file's limits are in its label, not in a placeholder or a tooltip;
- a file that is refused puts each reason in a notice above the form, sets `aria-invalid` on the file field and points its `aria-describedby` at the notice, and a notice at the top says nothing has changed;
- what a file would do is said in three sentences with their counts before any table, so nobody has to read a table to learn whether it is safe to confirm;
- the changes and the rows that cannot be read are tables with a header row. Each sits in a region named by its heading that scrolls sideways by itself and takes keyboard focus, so at 320 px the page does not scroll sideways and a keyboard can still reach every column;
- confirming is a button, and a file that would change nothing has none. The other button puts the file away;
- an import that runs is said in a sentence with its rows done, and a link draws the page again. Nothing refreshes by itself, so nothing moves under a reader.

`import.spec.ts` downloads the sheet, has a missing file, a file that is not a CSV and a file with nothing to import refused, reads what a file would change and the row it cannot read, confirms from the keyboard, and reads what the import did, with axe in each state, at desktop and phone widths and with scripts off.

**WooCommerce > Builder, Catalogue check.** The third tab, one form with one button, a plain post that works with scripts off:

- nothing is read until the button is pressed, so opening the tab is quick and moves nothing;
- the answer is a notice with `role="status"` that says how many things were found, or that nothing was, before any table;
- what was found is a table with a header row: where, the kit, and what to fix as a whole sentence that names the spec and the values. It sits in a region named by its heading that scrolls sideways by itself and takes keyboard focus, so at 320 px the page does not scroll;
- each part is a link, by its name and SKU, to the product's Part specs tab, where the field is;
- a list longer than 500 rows says how many more there are.

`check.spec.ts` runs the check from the keyboard, reads a part that names a chart the shop no longer has, follows its link, and runs it again once fixed, with axe before and after, at desktop and phone widths and with scripts off.
