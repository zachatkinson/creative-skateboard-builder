### What it builds

**The rule for every screen.** The server form stays the product.

- Each screen renders today's form. The script mounts DataForm or DataViews over it and writes the same field names into hidden inputs, so the same POST, nonce, capability check and server validation run, as WooCommerce's `form_post` does.
- Each field is described once, in PHP: label, help, type, limits and choices, translated. The template draws from it, and it is printed as JSON for the script. The admin's React draws nothing that description doesn't hold.
- The client's rules are hints, and the server decides every save. Server errors come back to their fields through DataForm's `validity`, with one notice at the top that links to each.
- Repeating groups get "+ Add", a remove on each row, reordering by Move up and Move down (and by drag, where DataViews allows it), and inline errors.
- **Without JavaScript,** every screen is today's.

### The public API it adds

Each goes in `docs/HOOKS.md` with `@since 1.5.0`, in `docs/SETTINGS.md` where it is a setting, and in the API snapshot:

- **Script and style handles,** one per screen, with today's kept: `cbuild-build-tab`, `cbuild-part-specs`, `cbuild-check`, `cbuild-import` and `cbuild-spec-tables`, plus `cbuild-settings` and the shared admin stylesheet. The names are fixed at the foundation.
- **The Catalogue check's bulk action:** its form field and action name, with its capability and nonce.
- **Saved views:** each user's view of a list, in core's `{prefix}persisted_preferences` user meta under the plugin's own scope, through `wp-preferences`. A `PRIVACY.md` line says what is kept and what uninstall does to the plugin's scope alone.
- **From the options audit, where an item earns its place** (the final list is set by the sort):
  - in `_cbuild_settings`: the new switches (Save build, Link to this build, Compare, the sides, the estimate), each on when absent; the slot's question; the assembly choice; where the 3D view opens;
  - in `cbuild_settings`: the Recommended order, and the kit new kits start from;
  - `cbuild_kit_text`'s new keys, `slot_question` and `add_to_cart`;
  - a filter, `cbuild_email_picture` (`bool $show`, `WC_Order $order`, `string $email_id`), true by default;
  - a CSS custom property, `--cbuild-maple`.
- **The release:** each GitHub release gains its CycloneDX SBOM beside the zip.

**Kept as they are.** No setting's stored shape changes, beyond keys added as above. `cbuild_settings`, every kit and part meta key the screens write and `cbuild_spec_table` stay as `schema/*.json` has them, so a rollback to 1.4.0 reads what 1.5.0 saved; `RollbackTest` holds it. The POST field names stay, since the hidden inputs send them. R1 to R8 get plain labels in the admin and keep their keys. The field description's JSON and the admin's scripts are private, as the store is. No route or table is added, and nothing public is renamed or removed.

### Risks, by dimension

| Dimension | What could go wrong | What catches it |
| --- | --- | --- |
| DRY and SOLID | Labels and rules written in PHP and TypeScript, drifting apart; the admin kit reaching into the builder's code, so a sibling can't copy it | One PHP field description printed as JSON, with a unit test that the template and the JSON match; deptrac's admin-kit layer and the ESLint import rule; `composer arch` |
| Anti-patterns | Validation only in the client; a list that still grows by saving; logic in a hook class | Integration tests that POST past the script with hostile values; the walkthroughs; hooks that call services, as today |
| Security | A hidden input trusted; a form or the bulk action without its capability or nonce; a combobox search that shows products to a user who can't edit them; the SBOM job holding the token | Server re-validation on every save; a capability and nonce test per form and for the bulk action; WooCommerce's own permission-checked searches, read before use; gate 9 on `release.yml`; CodeQL and the Scorecard themselves |
| Privacy | Saved views stored but not listed; uninstall removing other plugins' preferences, or none of ours | The `PRIVACY.md` line; an uninstall test that removes the plugin's scope and leaves another scope in the same meta |
| Accessibility | A modal that loses focus; a reorder only by drag; a sticky Save over the focused field; small targets; DataViews' list layout with a screen reader | axe on every state of every screen; keyboard tests per modal and per Move button (WCAG 2.5.7, 2.4.11, 2.5.8); the table layout only; the manual screen reader pass (question 1) |
| Internationalisation | The bundle's own strings in English in fr-ca; its RTL styles; a concatenated count in "12 parts name this chart"; the audit's new copy left untranslated | fr-ca and rtl on every screen; `_n()` and the patterns; `wp_set_script_translations()` per handle, the script JSON made at landing; `composer i18n:check` |
| SEO | An options audit item that changes the builder page's markup or its LCP, such as the estimate switch or the step's question | The builder's Lighthouse runs and budgets, unchanged; the admin screens themselves have no SEO surface |
| Performance | DataForm loaded on every product edit; a shared chunk on every screen; a large check paged in the browser; the new switches adding queries to the state route | Per-entry budget lines in `npm run budget` and CI; the Build tab on kits only and Part specs on opening; the check paged by the server, benchmarked at 2,000 parts; the query count with every new switch on and off |
