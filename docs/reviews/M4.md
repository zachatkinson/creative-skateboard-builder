# Milestone 4 review: Kits

Tag `v0.4.0` · planned 10 November 2026 · written by Claude Code; reviewed by spec-reviewer, auditor, then Claude in Cowork.

## Plan

### What it builds

The kit, and the first thing a visitor can reach: the route that says what fits.

1. **Owed first.** The thirteen minors listed in milestone 3's review (#19), and #20: a settings save asks for a reindex only when the mapping or the source order changed, which has to land before this milestone adds keys to the same option.
2. **The kit product type,** `cbuild_kit` (`KitProduct extends WC_Product`): virtual, not purchasable outside the builder, its fee in `_cbuild_assembly` and never in WooCommerce's price fields. Its four documents (`_cbuild_slots`, `_cbuild_rules`, `_cbuild_presets`, `_cbuild_assembly`) are read and written through the product's own CRUD, each checked against its schema in `schema/` with `rest_validate_value_from_schema()` and then by the domain's value objects, which milestone 2 built.
3. **The kit stays out:** of the catalogue and search (WooCommerce's visibility terms), of feeds, of WordPress's sitemap and Yoast's, and it prints no product markup.
4. **`Adapter\WooKits` replaces `Adapter\NoKits`** behind `Port\Kits`. The Catalogue check's kit findings then have kits to read (#17), and the Part specs panel shows only the specs a product's slots need (#16).
5. **The Build tab** on kit products: slots (a key made once from the label, Move up and Move down as well as drag), rules R1 to R8 with their settings, up to six presets, and assembly. A document that fails is not saved, the rest of the product saves, and the notice links each problem to its field. A preset is saved only when the rules accept it, and R7's quantities are checked here (D-062).
6. **The state service and its route,** `GET cbuild/v1/kits/{id}/state`: an argument schema (`picks[<slot key>]`, `previous[<slot key>]`, `step`, `assembly`, `locale`); each option's fit, the hidden counts and why, the change list when `previous` is sent, the recommendations, and the total with assembly in it. Public and read-only, with a rate limit (120 a minute by default, a salted hash of the address for its minute, 429 with `Retry-After`), `Cache-Control: no-store`, and a published JSON Schema its every answer is tested against. Within 80 ms at p95 with 500 candidates.
7. **Card data** for the options a step shows (name, photo, price, stock in the shop's own display format), primed in one query each and cached per part, keyed by the part's last change and a price context.
8. **The second half of #14:** a part's stock count checked against what a build takes of it (a slot's units per build over the part's set size).
9. **The abilities** `creative-skateboard-builder/check-build` and `creative-skateboard-builder/price-build`: read-only, the route's own service, in the category the Catalogue check's ability made.
10. **The filters** the answer runs through: `cbuild_part_available`, `cbuild_price_context`, `cbuild_slot_label`, `cbuild_preset_label` and `cbuild_kit_text`.
11. **The rest of the settings page:** defaults for new kits, the build discount, how coupons reach the parts, the route's rate limit and the trusted proxy header. Milestone 5 reads the discount and the coupon setting; the keys are public from here.

Not in this milestone: anything a shopper sees. The builder's page and block are milestone 6, the cart is milestone 5.

### Spec sections it touches

How it fits (the state route, the abilities); Data model (the kit and its four documents, Options and jobs); Compatibility rules (as the Build tab's switches and settings); The builder (what an answer holds: fit, hidden counts, the change list, recommendations, the total); Pricing, stock, assembly and returns (prices from the cart's own functions, stock read when asked, the fee); Admin (capabilities, the Build tab, the Part specs panel's "only the specs the product's kits need", the Catalogue check's kit rows, Settings); French and other languages (the route's locale); SEO and sharing (the kit stays out of search); Privacy and data handling (the rate limit); Security, performance and compatibility (the state route, what it shows, card data, Switched off safely, Upgrades and the public API, Resilience).

### The public API it adds

Each goes into `docs/HOOKS.md`, the snapshot and the changelog with the code that adds it. Names not fixed by the spec are settled as each lands and recorded.

- **Product type:** `cbuild_kit`.
- **Product meta:** `_cbuild_slots`, `_cbuild_rules`, `_cbuild_presets`, `_cbuild_assembly`. Their schemas have been public since 0.2.0.
- **REST route:** `cbuild/v1/kits/{id}/state`, with its arguments and its answer's schema, `schema/state.json`. `npm run types` generates the script's types from it.
- **Abilities:** `creative-skateboard-builder/check-build`, `creative-skateboard-builder/price-build`.
- **Filters:** `cbuild_part_available`, `cbuild_price_context`, `cbuild_slot_label`, `cbuild_preset_label`, `cbuild_kit_text`.
- **Settings keys** in `cbuild_settings`: the defaults for new kits, the build discount, the coupon setting, the rate limit and the trusted proxy header.
- **The object cache group** card data is kept in, if a shop's own code may clear it.

### Decisions I expect to record

- **Where the rate limit counts.** Not a table. A persistent object cache where the shop has one; a transient per hashed address for its minute where it has none, which is one small write a request. The salt is the site's, the hash is all that is kept, and the trusted proxy header is read only when the shop names one.
- **A kit switched off is safe by construction:** no price in WooCommerce's fields, so with the plugin off WooCommerce reads a kit as a simple product with no price and will not sell it. A test deactivates the type's class and asks WooCommerce.
- **What "feeds" means** for a product type that is hidden: WordPress's product feed, and WooCommerce's own product queries. Third-party feed plugins read visibility, which is set.
- **The Part specs panel's narrowing** (#16): a product in no kit's slot shows every group, as now, since a shop fills specs in before it builds a kit.
- **The state service is one class the route and both abilities call,** so they cannot disagree; a test runs the same builds through all three.
