# Milestone 2 review: Domain

Tag `v0.2.0` · planned 9 November 2026 · written by Claude Code; reviewed by spec-reviewer, auditor, then Claude in Cowork.

## Plan

### What it builds

All of it in `src/Domain`, which has no file yet, and none of it loads WordPress.

1. **Measures and specs.** A measure is a whole number of ten-thousandths in one unit (inches or millimetres), matching the index's `DECIMAL(10,4)`, so no rule compares floats. A parser for the edge reads decimals in either separator, fractions and mixed numbers (`7/8`, `8 1/4`, `8-1/4`) and unit marks, and refuses anything else. The spec keys are an enum, each with its unit and kind (measure, choice, flag, count).
2. **The model.** Slot, part (id, slot, brand, specs, price, stock, set size), picks, build, and the kit's four documents (slots, rules, presets, assembly) as value objects with `fromArray()`, each checking its own invariants and its `schema_version`. The JSON Schemas for those four go into `schema/`, so the shape is fixed once and milestone 4's Build tab validates against the same files.
3. **Rules R1 to R6** behind one interface, each returning a verdict: fits, warn or block, with the rule, its source and a message code with values. R7 as the quantity check and the units a build takes. R8 as the deck option's wheelbase and length, with no verdict.
4. **The fit engine.** Each slot's options against the picks before it, in step order; the hidden parts counted per slot and grouped by rule and reason; a part missing a required spec not offered, with its reason; the three optional specs defaulted and flagged.
5. **The change list**, with the closest fitting part and the undo.
6. **Recommendations.**
7. **Pricing.** Money in minor units; parts at the prices passed in; the fee; the build discount rounded per line.
8. **The build validator** the cart will use, which is the engine asked about a whole build.
9. **The picture's layout**: each layer's scale and position from the specs.
10. **Owed from milestone 1:** issue #6 (one coverage number for all of `src/`), issue #5 (`api:check` reads the changelog) and issue #9 (the dev toolchain's advisories; see For Zach).

### Spec sections it touches

Vocabulary; Data model (the kit's documents, part specs, `set_size`); Compatibility rules, all of it; The builder (recommendations, hidden parts, a change that breaks later picks, the picture); Pricing (the build discount, the fee, the $0 parent); Testing (unit, the invariant, benchmarks); Quality bar.

### The public API it adds

- **The four document schemas** in `schema/`: `slots`, `rules`, `presets`, `assembly`, each at `schema_version` 1. `docs/HOOKS.md` lists them, and `tools/api-surface.php` learns to read `schema/`, so a changed schema fails `api:check` without its snapshot, `HOOKS.md` and changelog lines.
- **The spec keys** and **the message codes**, which the specs index, the state route and translations will carry from milestones 3 and 4. They are listed in `HOOKS.md` and snapshotted now, so they can't drift before then.
- No hook, route, setting, option, table or meta key. The meta keys that hold the documents arrive with the kit in milestone 4.

### Installed source checked

The domain calls nothing in WordPress. Three things it must agree with later were read in wp-env's WordPress 7.1.4 and WooCommerce 11.2.2:

- `rest_validate_value_from_schema()`, `wp-includes/rest-api.php:2221`, as the spec names it. An integration test validates every domain fixture document against `schema/` with it, so the schemas and `fromArray()` can't disagree.
- `wc_get_price_decimals()`, `includes/wc-formatting-functions.php:568`. The domain takes the decimals as a number.
- `wc_round_discount()`, `includes/wc-core-functions.php:2488`, rounds half down (`WC_DISCOUNT_ROUNDING_MODE` is 2, `class-woocommerce.php:549`). The build discount sets each part's price, and is not a coupon, so it rounds the discounted price half up as WooCommerce rounds a price. To be recorded as a decision, and checked against the cart's own totals in milestone 5.

### Risks, by dimension

| # | Dimension | What could go wrong here | What catches it |
| --- | --- | --- | --- |
| 1 | DRY and SOLID | A second place decides fit: the validator, the change list or the recommender re-implementing a rule. Rules reading settings or stock through globals. One engine class doing everything | The validator, the change list and the recommender take the engine and call it; the invariant test fails if they disagree. `composer arch` (the domain depends on nothing). The auditor reads class sizes and the rule interface |
| 2 | Anti-patterns | Floats for measures or money; specs guessed from names; arrays of arrays in place of value objects; exceptions as control flow for a missing spec | Whole-number measures and money, with boundary tests at each tolerance. PHPStan level 10 with the strict rules. A missing spec is a verdict, with a test per rule |
| 3 | Security | The domain trusts a document's shape because the edge validated it, and a crafted one (a huge slot list, a negative price or quantity, a pick for a slot the kit lacks) gets through | Every `fromArray()` checks its own invariants and bounds, with a refusal test for each; the validator refuses a pick outside its slot's candidates |
| 4 | Privacy and data handling | None: the domain holds parts, specs and prices, and nothing about a person | The gate for WordPress in the domain; review |
| 5 | Accessibility | None directly. The risk is indirect: a verdict that carries too little for the page to say why (which rule, which values), leaving milestone 6 a vague fit label or a silent change | Every verdict, hidden group and change carries a code and its values; the tests assert them, not only the severity |
| 6 | Internationalisation | English in the domain; a unit or a fraction formatted there; a number carrying the shop's separator inwards | Message codes are an enum, and a test fails if a domain file holds a string with a space in it outside exception text. The parser takes the separator as an argument. The gate for WordPress in the domain |
| 7 | SEO | None: nothing here renders | Not touched |
| 8 | Performance | The engine re-reading the picks per option, or the closest-part search and the hidden grouping going quadratic | The benchmark at 500 candidates, and again at 1,000 and 2,000 to show the time growing in step; `docs/BENCHMARK.md` gets the figures |
| 9 | Testing | Tests written after the rules; boundaries missed, so mutants live; the seeded generator building only catalogues that fit; a floor quietly narrowed while the coverage report changes shape (issue #6) | The spec's cases are committed first and seen failing. 100 % lines and branches, and 100 % MSI on the domain. The generator's own test shows it makes blocked, warned and missing-spec parts. The merged floor is shown failing with a deliberately untested class in each group |
| 10 | Upgrades and compatibility | A document's shape, a spec key or a message code changing after others read it; a document from an older `schema_version` refused outright | The schemas, keys and codes are in the snapshot and `HOOKS.md`. `fromArray()` refuses a version it doesn't know with a code that names it, so milestone 4's migrations have something to act on |
| 11 | Resilience | One bad part (a missing spec, a zero set size, no price) throwing and taking the whole slot with it; an empty slot, no deck picked, or a pick that no longer exists | Each is a case: the part isn't offered and carries its reason, and the engine answers for the rest. The invariant run includes them |
| 12 | UX and content | A change list that swaps a pick without it being asked for (P8); a recommendation the shopper can't see (P9); a deck picked for them; hidden parts with no reason (P1) | The change list is a proposal and an undo, and applies nothing. The recommender refuses the deck slot. Each has a test named for its pattern |

### Order of work

Test-first items are marked **T**. `/verify` runs before each commit.

1. **Issue #6.** The integration suite with coverage in wp-env, a merge of its report with the unit suite's, the 90 % floor on the merged number, and the named exclusions out of `phpunit.xml.dist`. In CI it rides in the integration leg that already starts wp-env (D-040). Shown failing both ways.
2. **Issue #5.** `api:check` fails for a snapshot item its version's changelog entry doesn't name. Shown failing.
3. **T** Measures, units, the parser and the spec keys: conversions, fractions and every refusal.
4. **T** The model and the four schemas, with the integration test that holds them together.
5. **T** R1 to R6, one commit each: the spec's cases first, then both ends of each range, each tolerance and the missing spec. R3's seeds are checked against the spec's sources here, and any change recorded.
6. **T** R7 and the units a build takes.
7. **T** The fit engine and its hidden counts.
8. **T** The change list, then recommendations.
9. **T** Pricing: the discount per line, a currency without decimals, a $0 parent.
10. **T** The build validator, then the invariant over seeded builds on a generated catalogue.
11. **T** The picture's layout, at each width, length and wheelbase.
12. The benchmark, and its figures into `docs/BENCHMARK.md`.
13. `HOOKS.md`, the snapshot, the changelog, then `/audit-milestone`.

### Decisions I expect to record

Mine to make, each with its reason in `docs/DECISIONS.md` from D-049 as it is settled:

- measures and money as whole numbers, and how a fraction finer than four places rounds;
- the build discount's rounding (above);
- what "nearest spec" means per slot in the change list: nearest to the replaced part on the spec its failed rule reads;
- R1's tolerances as the kit's settings: one that widens a maker's range, default 0, beside the 0.25 in and 0.5 in for a truck with none;
- the usual wheelbase when a deck gives none: worked out from its length, then its width, from the spec's R8 sources, with the kit's own anchor overriding it in milestone 7;
- the layout's units: millimetres from the deck's centre, so milestone 7's template scale is one multiplication;
- the schemas ship now, and `api-surface.php` reads them.
