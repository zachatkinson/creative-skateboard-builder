# Milestone 3 review: Specs

Tag `v0.3.0` · planned 10 November 2026 · written by Claude Code; reviewed by spec-reviewer, auditor, then Claude in Cowork.

## Plan

### What it builds

The first milestone with WordPress in it since the foundation: everything between a shop's products and the domain's `Specs`.

1. **The specs index's repository.** Reads and writes `{prefix}cbuild_specs`, the table milestone 1 made. One row per part and spec: a number or a short text, its source, what in that source it came from, and when. The table does not change.
2. **Three sources behind one port** (`Port\SpecSource`): the part's own fields (`_cbuild_specs` meta, a variation left blank taking its parent's), the shop's attribute mapping, and the spec table and size a part names. A service, `SpecIndexer`, asks all three, takes the winner by the shop's order (the maker's chart first by default, D-026), and records every disagreement.
3. **The jobs.** `cbuild_index_part` for one part and `cbuild_reindex` for everything, 100 parts a batch from a saved cursor. Both idempotent. A product or variation save, a term change on a mapped attribute and a spec table's save each queue the parts they touch, and never index in the request.
4. **Spec tables.** The post type `cbuild_spec_table`, a row per size. A migration creates Independent, Thunder and Venture from the spec's table under R1, each row with its source and the date it was read. Their screen under WooCommerce > Builder. Saving one re-indexes the parts that name it.
5. **Settings**, at WooCommerce > Settings > Builder: the attribute mapping (attribute, spec, unit) and the order of the sources. The page's other settings arrive with the milestones that read them.
6. **The Part specs panel** on simple products and inside each variation: the unit shown, the shop's decimal separator or a fraction, inherited values read-only with where they come from.
7. **CSV import and export**, in the admin and as `wp cbuild specs import|export`: keyed on ID or SKU, a dry run that writes nothing, an export whose cells a spreadsheet cannot run.
8. **The Catalogue check**, in the admin and as `wp cbuild check`, which exits non-zero when it finds anything.
9. **The ability** `creative-skateboard-builder/catalogue-check`, for those who can manage WooCommerce.
10. **Site Health:** the index up to date, failed jobs.
11. **Owed from earlier milestones:** issue #14's first half (a part carries its stock count), and issues #2, #3 and #4, which Zach said to do now (see For Zach).

### Spec sections it touches

Data model (Part specs, the specs index, Options and jobs); Admin (capabilities, Part specs, Spec tables, Catalogue check, Import and export, Settings); Compatibility rules (which source wins, the seed tables, what the Catalogue check flags); Security (admin actions, the export's cells, uninstall); Performance (the index rebuilt in the background); Upgrades (a reindex that resumes); Resilience (failed jobs found); Privacy; Testing (integration and benchmarks).

### The public API it adds

Each goes into `docs/HOOKS.md`, the snapshot and the changelog with the code that adds it.

- **Actions (Action Scheduler):** `cbuild_index_part`, `cbuild_reindex`.
- **Post type:** `cbuild_spec_table`, and the shape of its rows.
- **Meta:** `_cbuild_specs` (a part's own specs), `_cbuild_spec_table` (the table and size a part names).
- **Settings keys** in `cbuild_settings`: `attribute_mapping`, `source_order`. Listed in `docs/SETTINGS.md`.
- **Index sources:** `field`, `attribute`, `table`, as stored in the index's `source` column.
- **WP-CLI:** `wp cbuild specs import <file> [--dry-run] [--key=<id|sku>]`, `wp cbuild specs export [<file>]`, `wp cbuild check`, `wp cbuild reindex`, each with its exit codes.
- **Ability:** `creative-skateboard-builder/catalogue-check`, with its output schema.
- **The CSV's columns**, which a shop's spreadsheet will be written against.
- **Site Health test ids:** `cbuild_index`, `cbuild_jobs`.
- **Hooks:** `cbuild_spec_sources` (a filter, so another plugin can add a source) is the only one I expect. None is added without a use.

## Review

Written on 10 November 2026, after the spec-reviewer and the auditor read the branch with fresh context and their findings were dealt with.

### What was built, against the plan

Every item under "What it builds" is built: the specs index and its three sources, the jobs, the settings tab, the makers' charts and their seed, the Part specs panel, Import and export, the Catalogue check, the three WP-CLI commands, the ability, Site Health's two tests and its Info section, and the 2,000-part benchmark. Issues #2, #3 and #4 are done (D-066, D-067), and the first half of issue #14 (a part carries its stock count).

Where the result differs from the plan:

- **Nothing indexed a catalogue that was already there** until the audit. The build indexed a part when it was saved and reindexed on a settings change; an install, an upgrade and an activation asked for nothing. Both reviews found it. Fixed (D-082).
- **The plan read Action Scheduler's unique flag from its function's comment,** which names the hook and group alone. The query compares the arguments too. The per-part job's own deduplication stays, for the reason that does hold: a running action counts as a duplicate (D-071, corrected).
- **The Catalogue check's kit findings have no kits to read yet.** `Adapter\NoKits` stands in until milestone 4's kits; the check's kit rules are tested with kits made from documents (D-077).
- **The Part specs panel shows every spec,** not only those a product's kit slot needs: a product's slot is not known before milestone 4 (D-074).
- **Site Health has two tests, not three.** The spec lists "the Catalogue check" beside the index and the jobs; the check reads every part, which a page that loads on every visit to Site Health should not do. The jobs test links to it (D-080). For Zach, 3.
- **One script, inline, on the product screen** (D-083). The plan had none. For Zach, 1.
- **Mutation testing leaves out more classes than the plan said,** without Zach's word, which D-038 asks for. For Zach, 2.
- **Test-first:** each step's spec cases were written with its code and committed together, as D-065 allows, with the red run in the commit's message. The audit's fixes each have a red run or a deliberate break, below.
- **The version is 0.3.0** in the header, the constant, `readme.txt` and `package.json`. No run-time dependency was added. One dev tool was: Redis and Redis Object Cache's drop-in for the object-cache leg, on Zach's answer (D-066).
