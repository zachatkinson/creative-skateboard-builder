# Milestone 3 review: Specs

Tag `v0.3.0` · planned 10 November 2026 · written by Claude Code; reviewed by spec-reviewer, auditor, then Claude in Cowork.

## Plan

### What it builds

The first milestone with WordPress in it since the foundation: everything between a shop's products and the domain's `Specs`.

1. **The specs index's repository.** Reads and writes `{prefix}cbuild_specs`, the table milestone 1 made. One row per part and spec: a number or a short text, its source, what in that source it came from, and when. The table does not change.
2. **Three sources behind one port** (`Port\SpecSource`): the part's own fields (`_cbuild_specs` meta, a variation left blank taking its parent's), the shop's attribute mapping, and the spec table and size a part names. A service, `SpecIndexer`, asks all three, takes the winner by the shop's order (the maker's chart first by default, D-026), and records every disagreement.
3. **The jobs.** `cbuild_index_part` for one part and `cbuild_reindex` for everything, 100 parts a batch from a saved cursor. Both idempotent. A product or variation save, a term change on a mapped attribute and a spec table's save each queue the parts they touch, and never index in the request.
4. **Spec tables.** The post type `cbuild_spec_table`, a row per size. A migration creates Independent, Thunder and Venture from the spec's table under R1, each row with its source and the date it was read. Their screen under WooCommerce > Builder. Saving one re-indexes the parts that name it.
5. **Settings**, at WooCommerce > Settings > Builder: the attribute mapping (attribute, spec, unit) and the order of the sources. The page's other settings arrive with the milestones that read them.
6. **The Part specs panel** on simple products and inside each variation: the unit shown, the shop's decimal separator or a fraction, inherited values read-only with where they come from.
7. **CSV import and export**, in the admin and as `wp cbuild specs import|export`: keyed on ID or SKU, a dry run that writes nothing, an export whose cells a spreadsheet cannot run.
8. **The Catalogue check**, in the admin and as `wp cbuild check`, which exits non-zero when it finds anything.
9. **The ability** `creative-skateboard-builder/catalogue-check`, for those who can manage WooCommerce.
10. **Site Health:** the index up to date, failed jobs.
11. **Owed from earlier milestones:** issue #14's first half (a part carries its stock count), and issues #2, #3 and #4, which Zach said to do now (see For Zach).

### Spec sections it touches

Data model (Part specs, the specs index, Options and jobs); Admin (capabilities, Part specs, Spec tables, Catalogue check, Import and export, Settings); Compatibility rules (which source wins, the seed tables, what the Catalogue check flags); Security (admin actions, the export's cells, uninstall); Performance (the index rebuilt in the background); Upgrades (a reindex that resumes); Resilience (failed jobs found); Privacy; Testing (integration and benchmarks).

### The public API it adds

Each goes into `docs/HOOKS.md`, the snapshot and the changelog with the code that adds it.

- **Actions (Action Scheduler):** `cbuild_index_part`, `cbuild_reindex`.
- **Post type:** `cbuild_spec_table`, and the shape of its rows.
- **Meta:** `_cbuild_specs` (a part's own specs), `_cbuild_spec_table` (the table and size a part names).
- **Settings keys** in `cbuild_settings`: `attribute_mapping`, `source_order`. Listed in `docs/SETTINGS.md`.
- **Index sources:** `field`, `attribute`, `table`, as stored in the index's `source` column.
- **WP-CLI:** `wp cbuild specs import <file> [--dry-run] [--key=<id|sku>]`, `wp cbuild specs export [<file>]`, `wp cbuild check`, `wp cbuild reindex`, each with its exit codes.
- **Ability:** `creative-skateboard-builder/catalogue-check`, with its output schema.
- **The CSV's columns**, which a shop's spreadsheet will be written against.
- **Site Health test ids:** `cbuild_index`, `cbuild_jobs`.
- **Hooks:** `cbuild_spec_sources` (a filter, so another plugin can add a source) is the only one I expect. None is added without a use.

### Decisions I expect to record

Mine to make, each in `docs/DECISIONS.md` from D-066 as it is settled:

- **The Builder settings tab arrives now, with two settings.** The roadmap lists the page under milestone 4, and D-026 says the mapping and the source order land in milestone 3. The index cannot be built without them.
- **The Catalogue check comes before kits exist.** It reads kits through a port. This milestone's adapter finds none, since the kit product type is milestone 4's, so in the admin it reports what needs no kit: parts whose sources disagree, rows the index could not read, parts naming a table or size that does not exist, failed jobs. The kit-dependent findings (a missing spec a slot's rule needs, a preset that no longer fits, a slot with nothing in stock) are built and tested now against kits made from fixture documents, and switch on when milestone 4 supplies the adapter.
- **A slot's candidates** (the parts its categories, brands, products and attribute terms name) are found by one service through WooCommerce's CRUD, since the check needs them now and the state route will in milestone 4.
- **One job per part without losing any:** how `cbuild_index_part` is deduplicated, given what Action Scheduler's unique flag compares.
- **The import between its dry run and its confirmation:** where the rows wait, for how long, and who may confirm them.
- **The CSV's shape:** columns, the key column, encodings accepted, the size cap.
- **How a variation names a table and size**, and what a spec table's row stores.
- **The reindex's cursor** lives where milestone 1's migrations keep theirs, or in an option of its own.

### Risks, by dimension

| # | Dimension | What could go wrong here | What catches it |
| --- | --- | --- | --- |
| 1 | DRY and SOLID | Three sources each parsing values their own way; the panel, the import and the CLI each validating a spec differently; the indexer knowing about WooCommerce; fit decided in the Catalogue check | Every value from every edge goes through `MeasureParser` and `Specs::with()`. One `SpecWriter` service behind the panel, the import and the CLI. deptrac: services see ports only. The check asks `FitEngine::judge()` and holds no rule |
| 2 | Anti-patterns | Indexing in the save request; `get_post_meta()` or SQL for products where CRUD exists; a hook holding logic; a God "Specs" class; option autoload bloat from the mapping | The integration test that a product save runs no index query. Gates 1 and 6, PHPStan's disallowed calls. Hookables are one line into a service. The settings option is one small array |
| 3 | Security | An import that writes without the capability or the nonce, or confirms someone else's dry run; a CSV cell that runs in a spreadsheet; a huge or malformed file exhausting memory; a path from the CLI or the upload read where it should not be; stored XSS through a spec table's name or a source label; the variation hook trusted for its nonce | Every admin action tested with and without its capability and nonce. The export's formula test, each of `=`, `+`, `-`, `@`, tab and carriage return. A row and size cap, streamed reading. The upload goes through WordPress's own handler and is never executed or kept. Escaping tested on the read-only "where it comes from" labels. The plugin's own `edit_products` check on both save hooks |
| 4 | Privacy and data handling | None about a person: specs describe products. The risk is the record: new meta, a post type, an option and a waiting import not listed, or left behind on uninstall | `docs/PRIVACY.md` and `docs/SETTINGS.md` updated with each. `UninstallTest` extended to the meta, the posts, the option and any waiting import, on a single site and a network |
| 5 | Accessibility | The first real screens. A keyboard-path test for each. Each error linked to its field with `aria-describedby`. `docs/A11Y.md` gains the screens |
| 6 | Internationalisation | The decimal separator: a fr_CA shop types `8,25` and the export writes `8.25`, or the other way; a unit or a source label concatenated into a sentence; CLI messages untranslated; the CSV's headers translated, so a file from one locale fails in another | Parser tests through the edge at both separators. The CSV always uses a point and fixed English headers, documented. `fr-ca` and `rtl` browser projects on the panel. The copy gate on the POT |
| 7 | SEO | A spec table post type that is public, queryable or in sitemaps | Registered non-public, not queryable, excluded from search. An integration test asserts it, and that it is absent from WordPress's sitemap |
| 8 | Performance | A product save that indexes inline; a reindex that loads 2,000 products at once; candidate or index queries that scan; the panel loading every spec table on every product screen; the check timing out on a large catalogue | The benchmark group: `EXPLAIN` on each index query must use a key, and the 2,000-part rebuild's time is recorded in `docs/BENCHMARK.md`. A query count on a product save. Batches of 100 with products primed in one query each. The check pages its work |
| 9 | Testing | Integration tests leaning on state another test left (Search's `reviews/M1.md` quirk); Action Scheduler's tables not reinstalled; the 95 % merged floor missed on admin code that only a browser reaches; the unit suite mocking WordPress into something it is not | Services are tested with in-memory ports in the unit suite and with real WooCommerce in integration. Admin controllers are thin and covered by integration tests that call them with a request. Each test makes its own products. Commits carry their red run (D-065) |
| 10 | Upgrades and compatibility | The seed migration running twice or overwriting a table the shop edited; a reindex interrupted by a deploy leaving half an index; meta or a setting key renamed later; a row written by a newer version breaking an older one | The seed migration is idempotent and never touches an existing table, tested by running it twice and after an edit. A reindex stopped halfway and resumed ends as an uninterrupted one does, with no duplicate row. Keys in the snapshot. `Specs::fromIndex()` already passes over what it cannot read (D-064) |
| 11 | Resilience | A part's job dropped because another part's is pending (Action Scheduler's unique flag); a failed job vanishing; a product deleted between queue and run; a spec table deleted while parts name it; a save during a reindex losing the newer value | Per-part deduplication tested with two parts queued together. | 12 | UX and content | An owner told "invalid value" with no field or reason; a dry run that hides what it will overwrite; the check listing problems with no way to fix them; jargon ("index", "source") in the owner's words | Each refusal names the field, the value and what would be accepted.
