# Milestone 5 review: Cart and checkout

Tag `v0.5.0` · planned 11 November 2026 · written by Claude Code; reviewed by spec-reviewer, auditor, then Claude in Cowork.

## Plan

### What it builds

A build in the cart, kept whole on every route, and written to the order by both checkouts.

1. **Owed first.** The CI and StrykerJS housekeeping Zach agreed on 11 November (#31, #32), then #21: a stock-only save queues no index job, which has to land before orders start reducing stock.
2. **Adding a build,** the same three steps through the Store API's `cart/add-item` and through WooCommerce's own form:
   - the whole build validated (slots, rules, stock, each part counted across every line already in the cart), from the parts as WooCommerce has them at that moment and never from the parts table (#26);
   - the build attached to the kit's line with a UUID, so two identical builds stay two lines;
   - a child line added per part, at the quantity the slot's units and the part's set size give.
3. **Keeping it together:** the parent's quantity sets the children's; removing either end removes the build, without the two calling each other; a child's quantity is locked and a change to it alone is refused; the parent's maximum is what the scarcest part allows; orphans are dropped and every build is checked again when the cart is checked.
4. **Showing it** in three carts:
   - the Cart and Checkout blocks, through Store API data on the cart item and a small script that answers `cartItemClass`, `itemName` and `showRemoveItemLink`, loaded on the cart and checkout pages only (D-010);
   - the Mini-Cart, through each part's item data and the `cbuild-part` class, with no script;
   - the classic cart, mini-cart widget and checkout, through WooCommerce's PHP filters.
5. **Prices and coupons:** each part at its live price; the assembly fee on the kit's line, or $0; the build discount from the settings, with the part's own price struck through; coupons following the kit to its parts, and a fixed product coupon landing where the setting says.
6. **One cart count per build** (D-009).
7. **Orders:** both checkouts write each line's keys and the parent's snapshot; once the order is saved, cart keys become order item IDs. The plugin writes no stock.
8. **Express pay:** a kit that arrives without a build is refused on every route, and the buttons are hidden on a kit's page where the payment plugin has a filter for it.
9. **Delivery data:** the filters `cbuild_arrival_estimate` and `cbuild_delivery_line`, asked by one service that milestone 6's summary shows; the returns notice carried onto the order for milestone 8's emails.
10. **A build in one shipping package,** for a shop whose packages are split.
11. **Carried from milestone 4:** tax by where the shopper is on the state route (#27), now that the cart knows the customer; the listed minors (#29); issue #25's three mutants and #22's quarantine, each looked at again.

Not in this milestone: the builder's page, the Edit build link and the event the builder sends after an add (milestone 6); the kit line's composed picture (milestone 7); order emails, the Build box and the assembly ticket (milestone 8).

### Spec sections it touches

How a build travels (steps 2 to 4); Data model (Cart items, Order items); Cart, checkout and orders, all of it but the picture and the order screen; Pricing, stock, assembly and returns (Pricing, Stock, Shipping; Assembly's fee; the returns notice as data); Security, performance and compatibility (Express payment buttons, the Mini-Cart, the 300 ms add to cart); Testing's integration and browser lists for the cart.

### The public API it adds

Each goes into `docs/HOOKS.md`, the snapshot and the changelog with the code that adds it.

- **Cart item keys:** `cbuild` and `cbuild_children` on the kit's line; `cbuild_parent` and `cbuild_slot` on a part's.
- **Order item meta,** hidden: `_cbuild_id`, `_cbuild_role`, `_cbuild_parent`, `_cbuild_children`, `_cbuild_slot`, and `_cbuild_snapshot` on the parent. Visible on the parent: Assembly, and the build in a line. These keys are forever.
- **Store API data** on `cart-item`, under the namespace `creative-skateboard-builder`: the line's role, build, parent and slot, with a schema.
- **Filters:** `cbuild_arrival_estimate`, `cbuild_delivery_line`, and one for keeping a build in one package, named when it lands.
- **Refusal codes** the cart answers with, each with its sentence.
- **The class `cbuild-part`** on a part's item data, which a theme may style.
- **Script handle** of the cart script, if a shop's code may dequeue it.

Two differences from the spec, each a decision to record with its code:

- **There is no one hook after the order is saved on both checkouts.** `woocommerce_checkout_order_processed` (`includes/class-wc-checkout.php:1450`) fires on the classic path alone, and `woocommerce_store_api_checkout_order_processed` (`src/StoreApi/Routes/V1/Checkout.php:708`) on the Store API's. Cart keys become item IDs on both, through one service.
- **Copying the keys onto an order item must be safe to run twice,** since the Store API runs it for each draft.

Still to find before the code that leans on them: how the Mini-Cart prints an item data entry's class in 11.2.2 (the spec read it on the demo in 11.2.1); the hook a stock-only change fires (#21); and the filter WooCommerce Stripe Gateway and WooPayments give for hiding their buttons on a product page. Neither payment plugin is in wp-env; their public source is read, not run.

### Decisions I expect to record

- **One cart service, and hooks that only call it.** `Service\BuildCart` validates, attaches, adds, syncs and removes; `Hooks\CartHooks` holds no logic. The domain's `BuildValidator` and `Pricer`, which have been there since milestone 2, decide fit and price.
- **The removal guard is state on the service,** not a static or a global: the build being removed is noted, and a removal that arrives for one of its own lines is let through without starting another.
- **Parts are read from WooCommerce when a build is added and when the cart is checked** (#26), seven products at most, loaded once a request.
- **The cart script uses WooCommerce's global** (`window.wc.blocksCheckout`) with `wc-blocks-checkout` as its dependency, so no build tool is added for WooCommerce's packages.
- **"The shop's own shipping methods" in CI are WooCommerce's:** flat rate, free shipping and local pickup. A carrier's plugin cannot run there. For Zach's eye, below.
- **The express buttons' filters are answered without the payment plugins installed.** The test calls the filter as the plugin would; Claude in Cowork checks the kit's page on the demo.
- **The order item keys' shapes,** written down before the first order is made with them.

## Review

Written on 11 November 2026, after the spec-reviewer and the auditor read the branch with fresh context and their findings were dealt with.

### What was built, against the plan

Every item under "What it builds" is built: a build added by the Store API and by WooCommerce's form, kept whole on every route, shown grouped in the Cart and Checkout blocks, the Mini-Cart and a classic cart, mini-cart widget and checkout, priced with the fee on the kit's line and the build discount on each part, counted once, written to the order by both checkouts, kept in one shipping package where the shop assembles it, and kept off the express buttons. Issues #21, #26, #27, #31 and #32 are done, #29's ten minors each have a line in D-136, and #22 and #25 were looked at again.

Where the result differs from the plan:

- **The hook classes are `Cart\*Hooks` and `Order\OrderHooks`,** not `Hooks\CartHooks`, and they held logic until the audit: a line's price, an order's ties and its snapshot. That is in `Service\BuildCart` and `Service\OrderBuilds` now (D-138).
- **Order again was not in the plan or the spec.** The audit found WooCommerce's button left a build's parts in the cart as loose lines. Zach chose to have the build put back whole (D-137).
- **A coupon's own exclusions hold inside a build** (D-137). The plan said coupons follow the kit; read alone, that let a coupon discount a part it leaves out.
- **Tax by where the shopper is (#27)** went further than the route: the two abilities price the same way, on Zach's answer, and the route finds the shopper without making a cart (D-135, D-138).
- **A build's parts are read together** (D-134). The first benchmark measured 132 queries for an add and 84 for a cart read; they are 54 and 30.
- **The add's benchmark has a ceiling of 450 ms on CI's shared runners,** as the state route's has 120 (D-124). The reviewer asked that Zach be asked; he was, and keeps it (D-137).
- **Eleven classes are named in the mutation exclusions,** on Zach's answer and by D-087's rule (D-138).
- **Composer's scripts have 30 minutes** in place of 300 seconds: the integration suite with coverage passed five minutes at 402 tests (D-138).
- **A must-use plugin in the browser site** switches a page to the classic cart and checkout for the tests that ask (D-132). It is a test fixture and ships in no zip.
- **Test-first:** each step's spec cases were written with its code and committed together, as D-065 allows, with the red run in the commit's message. The audit's fixes each have a red run and a deliberate break, below.
- **The version is 0.5.0** in the header, the constant, `readme.txt` and `package.json`. No run-time dependency, no dev tool and no table was added.
